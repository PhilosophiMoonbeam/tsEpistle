# Personalized site-logo particle treatment: implementation contract

## Source binding and review history

This document now governs the current working-tree pipeline-v5 contract; historical reviewed and deployment evidence remains dated and unchanged.

A focused correctness review found that redundant per-context CDP cache toggling caused the traced `net::ERR_NETWORK_CHANGED`; the toggle was removed because fresh BrowserContexts isolate cache state.

A focused lifecycle/performance review found that Tres loop stop order raced `Timer.disconnect`; a minimal patched `@tresjs/core@5.8.3` dependency now pauses/cancels RAF before disconnecting `Three.Timer`. The corrected browser gate has not yet been rerun on a rebuilt image, so these entries record resolved findings only and make no pass, build, deploy, or live-result claim.

## 1. Decision and non-goals

The prior interpretation as a fixed **Indigo Signal Field** was wrong. There is exactly one active branding source: the one image uploaded in tsEpistle Admin. A successful candidate drives both the ordinary site logo and one personalized login particle treatment in light and dark themes. The login treatment is decorative and never participates in authentication.

The Admin General page (`/general`, `manage:system`) provides one dedicated logo upload. The upload is processed automatically and asynchronously. The previous active ordinary logo and effect remain visible while processing and on failure; the new ordinary logo and effect activate together only in one successful, fenced transaction. Existing URL-only or default `logoUrl` values migrate unchanged and remain static-only until replaced. The server never fetches an arbitrary URL. There is no separate tsEpistle particle fallback.

The large field is optional decoration, not a replacement for `.login-brand`, `siteConfig.logoUrl`, `siteConfig.title`, or `#login-site-title`. Mobile, coarse-pointer, short-viewport, and insufficient-space layouts omit only the large field; the ordinary logo remains. Reduced-motion eligible desktop users receive the personalized static effect, without WebGL or animation.

## 3. Admin API, database authority, and transactions

### Upload and status API

Add dedicated `manage:system`-only endpoints: `POST /_api/site/logo` accepts exactly one multipart image and never accepts a URL; `GET /_api/site/logo` returns current active and candidate status; `POST /_api/site/logo/retry` retries the current failed candidate. Authorization occurs before multipart acceptance. Enforce a fixed `5,242,880`-byte source ceiling even when generic upload limits are larger. Admin General uses a dedicated one-file picker/drop target, not the generic media browser or `POST /u`, and states that the one shared immutable ordinary `logo-png` URL/bytes and personalized effect are public on login, navigation, favicon, and email surfaces. Remove `logoUrl` from the ordinary General save payload so an old open form cannot overwrite activation. Also fence the existing `PUT /_api/site/config` server-side: when either `siteLogoState.desiredRevisionId` or `activeRevisionId` is non-null, any supplied `logoUrl` is rejected with HTTP `409` and safe code `MANAGED_LOGO_CONFLICT`; in that fenced branch, every generic config save, whether or not the request includes `logoUrl`, omits `logoUrl` from `saveKeys` so generic code never persists it; only the dedicated activation transaction writes it. While both pointers are null, legacy `logoUrl` writes remain allowed unchanged. A failed desired candidate keeps this fence until cleanup, under the singleton lock and locked recheck, clears `desiredRevisionId` and retires/deletes that failed candidate; only after that commit is the fence released, and an active revision still keeps it in force.

Upload returns `202` with a revision/status URL when work is needed, or `200` when an existing ready revision is activated. The no-store status response exposes only safe error codes (`UNSUPPORTED_IMAGE`, `IMAGE_TOO_LARGE`, `INVALID_IMAGE`, `NO_VISIBLE_PIXELS`, `UNSUITABLE_LOGO`, `PROCESSING_FAILED`, `ARTIFACT_TOO_LARGE`) and shows the still-active preview plus candidate state: Uploading → Processing → Active or Failed. Raw decoder errors and stacks remain server logs with job/revision IDs. Retry does not alter the active revision.

### PostgreSQL schema

PostgreSQL is authoritative; local files are an optional atomic read-through cache keyed by the composite `(kind, final content hash)`.

- `siteLogoObjects`: immutable blobs keyed by composite `(kind, sha256)` of actual bytes; `kind` is exactly `source`, `logo-png`, `particle-v1`, or `effect-static-png`. A ready revision publishes exactly three derived objects: one ordinary `logo-png`, one `particle-v1`, and one `effect-static-png`; only those three derived kinds are public. The single `logo-png` object and its URL are shared byte-for-byte by login, navigation, favicon, and mail. Source is private; no surface-specific, theme-specific, backplate, or on-demand-composited object exists.
- `siteLogoRevisions`: UUID, source hash, integer pipeline version (new candidates use `SITE_LOGO_PIPELINE_VERSION=5`; v1/v2/v3 are legacy, v4 is the prior active contract), `pending | running | ready | failed`, durable job ID/retry sequence, exactly three derived hashes (`logo-png`, `particle-v1`, and `effect-static-png`), revision metadata columns `normalizedWidth`, `normalizedHeight`, `particleCount`, and `medianStroke` (nullable while `pending | running | failed`, required and output-validated for `ready`), plus nullable validated `auraColor`, safe error code, requester, and timestamps. `aspect` is derived as `normalizedWidth / normalizedHeight`, never stored as a second authority.
- `siteLogoState`: one installation-global row with monotonic generation, `desiredRevisionId`, and `activeRevisionId`. Foreign keys prevent deletion of desired/active data and use the expected object kind with each hash. Status reports desired state; serving uses active only.
- Source identity uses actual source-byte SHA-256; every derived object hash is computed from its final bytes, never from a logical path, source path hash, or revision ID. Every foreign key and database/object lookup supplies and validates both the expected role/kind and hash; a hash match with the wrong role is invalid.
Treat a stored object as immutable only while its bytes verify the declared `(kind, sha256)` identity. A hash/content mismatch is integrity corruption, not a valid immutable value: lock the singleton, object row, and referencing revisions before recovery; valid object rows are never mutated.
- Keep `settings.logoUrl` byte-for-byte for legacy compatibility. Unmanaged installations retain the exact legacy/default value. Managed activation writes the one immutable public `logo-png` URL, used identically by login, navigation, favicon, and mail, in the same transaction as `activeRevisionId`; `logoUrl` is not particle eligibility.

The upload/source/revision/job enqueue occurs in one transaction using `DurableJobStore` and the existing Knex transaction. Lock the singleton state. DB failure rolls back all four effects; do not mutate `WIKI.config` before commit or use unchecked `saveToDb` return as commit protocol. Before any same-source shortcut, validate the active revision's source object and all three derived objects by expected composite `(kind, sha256)` identity and by hashing their stored bytes. If any active object is missing or mismatched, preserve `activeRevisionId` and its existing URLs, never return `ready`, and enqueue fenced repair candidate work; when the uploaded bytes have the active source hash, atomically restore only the corrupt private source row from those hash-verified bytes. Exact active bytes return `ready` only after that validation succeeds. Exact pending or running bytes return that same candidate when its source object validates and every already-present referenced object passes the same validation; derived objects not yet staged are expected while processing. This preserves concurrent-upload deduplication and idempotency. A previously `ready` non-active revision is eligible for immediate reuse only under this lock and only after the source object and all three derived objects exist, each matches its stored SHA-256 and expected kind/role, and every composite-key lookup resolves to the expected immutable bytes. If such a ready row is corrupt or incomplete, mark it retired (or delete it when unreferenced) under the lock and create a fresh UUID revision with the next retry sequence and a new job; the absent uniqueness constraint cannot block that replacement. A matching failed revision is never reused as ready: a retry retires the failed candidate under the lock and creates a fresh UUID/retry-sequence revision/job, while an unreferenced failed or incomplete row is retired as appropriate. A cleaned match has no reusable row or objects and creates fresh work. Different bytes under the same filename always create a new source/revision.
### Handler protocol rollout and rollback

The handler protocol is distinct from the `particle-v1` binary wire format. Historical pipeline v4 uses `process-site-logo@2`; pipeline v5 uses `process-site-logo@3`; legacy v1/v2/v3 uses `process-site-logo@1`. The rollout is capability-fenced: final workers advertise all three protocols, but the default `@1` and `@2` handlers are terminal-replay/fail-safe only. A paired `ready` or `failed` old revision is a no-op; a paired `pending` or `running` old revision becomes failed with `PROCESSING_FAILED` without reading source, invoking pipeline v5, or publishing any output, after which retry creates `process-site-logo@3` pipeline-v5 work. Deploy version-aware web renderers and drain or inactivate every old web renderer before enabling `@3` workers to process or activate v5, because old clients cannot interpret v5 core sizing. Only after that drain may new `@3` work be enabled and enqueued. Active v4 remains authoritative and served while v5 is pending or failed; rollback stops new `@3` enqueue, preserves active branding, and uses lease/revision fencing. A v5 payload is never interpreted as v4 or legacy work. This ordering is a release requirement, not a claim that deployment or live activation has occurred.
For a mismatching object row, corruption recovery locks that row and every referencing non-active revision, atomically quarantines/deletes or marks each non-active reference retired before replacement work, and never leaves a ready row pointing at corrupt bytes. If an active source or derived row is corrupt, it is not deleted out from under the active pointer: the active pointer remains authoritative and is not cleared while unaffected valid surfaces continue serving; a fenced repair candidate stages replacement outputs privately. Its publish transaction may replace that mismatching row in place only with bytes whose SHA-256 equals its declared `(kind, sha256)` (or insert the missing row), atomically restoring all references; public reads remain `404` for the mismatching object until that commit. A repair or same-byte retry is idempotent under the same singleton/object locks, and valid rows are never rewritten.

Retire superseded revisions without mutating their objects. A daily durable cleanup takes the singleton lock, rechecks that a retired revision is still neither `activeRevisionId` nor `desiredRevisionId` and has remained retired for at least 37 days, then atomically deletes that revision row and any now-unreachable source/derived objects in the same transaction; no ready row survives object deletion for later reuse. Active and processing sources/bundles are never age-deleted. Failed desired revisions remain retryable for 37 days; cleanup may clear `desiredRevisionId` and delete that failed revision and its now-unreachable objects in the same lock-and-recheck transaction. Durable-job history may expire independently, so revision status cannot require a permanent job foreign key.

The current durable handler reads source bytes from PostgreSQL, never HTTP, local cache, uploads, or storage; default legacy `@1`/`@2` handlers fail nonterminal paired revisions before any source read. Capability-aware claiming filters by the worker-advertised handler protocol before lease ownership, so an older worker cannot claim pipeline-v5 `process-site-logo@3` work. Derived insertion is idempotent. Before inserting or publicizing any candidate bundle, measure the final binary raw and gzip-9 bytes and both PNG byte lengths against §8; an oversize candidate is marked failed with `ARTIFACT_TOO_LARGE`, leaves no derived public objects or URLs, preserves the old active revision, and publishes nothing. Publication locks the job and singleton state, verifies the exact running lease owner/token and an unexpired lease, and checks budgets before insertion.


## 4. Input validation and automatic processing

Initial managed formats are static PNG, JPEG, and WebP. Reject SVG, GIF/APNG, AVIF/HEIF, TIFF, PDF, multipage or animated inputs, corrupt/truncated/polyglot or MIME-spoofed data, and decompression bombs. Existing SVG and external URL logos remain valid static legacy values only. Hash actual bytes; ignore filename, extension, and claimed MIME for identity/type. Source bytes must not exceed `5,242,880`.

After format validation and EXIF orientation, require each dimension `64..4096`, total pixels `<=16,777,216`, at most four channels, and visible pixels. Use Sharp `0.35.4` with `failOn: 'warning'`, `limitInputPixels: 16_777_216`, `limitInputChannels: 4`, `unlimited: false`, `autoOrient: true`, metadata inspection, sRGB RGBA normalization, and no enlargement. Accept a static input when `(metadata.pages ?? 1) === 1`; reject a reported page count `>1`, validate `pageHeight` only when present and inconsistent with a single frame (`pageHeight !== metadata.height`), and retain explicit animated-container rejection rather than silently selecting a first page. The particle pipeline version changes whenever particle normalization, masking, sampling, encoding, or artifact schema changes; those particle-only version refinements do not alter the ordinary canonical branch.

Use native alpha when present. For opaque inputs, the particle/static branch alone may conservatively estimate a matte from a 3%-short-axis edge band clamped to `2..24` px: near-neutral means OKLab chroma `C <= 0.03`, and the matte is the component-wise alpha-weighted median OKLab of qualifying edge pixels (weight = source alpha). Use 8-connectivity for edge-connected clusters and mask components. Remove only a cluster with at least 85% total-border membership and at least 70% membership on each edge at OKLab delta `<=0.035`; for distance `d` from the matte, retained alpha is `0` at `d <=0.035`, linear `(d-0.035)/0.035` for `0.035<d<0.070`, and unchanged at `d >=0.070`. If constraints fail, preserve a genuine full-bleed badge and do not remove its background. When removal is attempted, retained-alpha fraction is `sum(generated alpha) / (255 * pixelCount)` and must be `>=2%` and `<=85%`; a meaningful connected component is one with at least `0.25%` of original alpha mass, and its disappearance rejects the mask. Trim only transparent/removed-matte padding, never foreground; deterministic normalization and the exact 4% per-side internal source padding apply only to the particle/static branch.
First decode accepted JPEG/PNG/WebP after auto-orientation to canonical sRGB RGBA raster `C`. The ordinary `logo-png` branches from validated `C` before every particle transform and is encoded losslessly as the full-canvas canonical upload appearance, preserving canvas, source colors, alpha, and aspect. The particle/static branch alone may apply the validated matte decision, transparent trim, linear-light premultiplied downsampling without enlargement, deterministic 4% padding, and source-alpha sampling. Let `componentCount` be meaningful 8-connected components, `occupancy=sum(alpha_i)/(255*pixelCount)`, and use `N=min(8000,max(2000,roundHalfAwayFromZero(8000*sqrt(occupancy)),8*componentCount))`. Pipeline v5 generates `N=2,000..8,000` records with eight deterministic reserved samples per meaningful component. Static and animated presentation preserve the core two-thirds quality target; full reconstruction remains required at IoU `>=0.75`.

The full-canvas ordinary `logo-png` is the lossless canonical `C` output defined above and is the same immutable ordinary branding on login, navigation, favicon, and mail. The particle/static raster alone retains deterministic 4% padding and any validated matte removal/trim. Pipeline v5 uses deterministic sampling with eight reserved samples per meaningful connected component, generates `N=2,000..8,000` records, and requires reconstructed-mask IoU `>=0.75`; the exact fixed vector is recorded, and an estimate is not a substitute.

Run preprocessing with concurrency one per process. A durable-job abort signal does not cancel native libvips work or bound RSS; release gates therefore measure each fixture in an isolated fresh child, recording absolute child `maxRSS` and wall time bound to that exact fixture's SHA-256 and source byte length. Cumulative RSS sampling across a reused worker is not valid evidence. Never claim an in-process Promise timeout cancels native work. Sharp is a production dependency only after final Alpine x64/arm64 (musl >=1.2.5; x64 SSE4.2), non-root Bun 1.4 fixture gates, optional dependency preservation, exact dependency policy, supply-chain review, and Sharp Apache-2.0 plus bundled libvips prebuild LGPL-3.0-or-later license/notice review pass. If those gates cannot establish bounded in-process operation, the implementation must use a killable resource-bounded subprocess before release.

## 5. Visual and responsive contract

The uploaded mark's arbitrary aspect ratio is authoritative. Measure free space between card and viewport padding; contain the padded particle/static mark with 8% clear space on every side, never crop or stretch. The wrapper and card rectangles must not intersect and must not cover dialogs, validation messages, or focus rings. Preserve the small ordinary `.login-brand` as the full-canvas canonical upload appearance in every state.

One source-derived geometry/color dataset serves both themes. Particle cores retain source color and alpha; colors are never quantized to a product palette and there is no generic purple/indigo identity. At runtime resolve the current Vuetify field-background color and choose black or white per particle to maximize outline-to-background contrast. Low-contrast cores receive a 1.25..2 CSS px neutral ring. At least 95% of alpha mass must have direct-or-ring contrast `>=3:1` in both themes. An aura may use the dominant chromatic source color at `<=8%` alpha; neutral marks omit it. Theme changes update only particle background/outline/aura uniforms and CSS variables, never geometry, source colors, or ordinary-logo bytes. The transparent static particle rendition uses the same fit and source colors. The one immutable `logo-png` is the only ordinary-logo rendition: its identical URL and bytes are the full-canvas canonical upload appearance on login, navigation, favicon, and mail. No CSS backplate, server-composited surface variant, per-theme asset, or extra role/hash is permitted.
The full-size core footprint is `D_norm=1+15*sizeNorm` normalized source pixels (range `1..16`) and is used only for ordinary reconstruction and IoU rasterization. Static effect presentation and the animated core apply an exact `2/3` size to that footprint; fitted static presentation scales the resulting diameter by `renderedLongAxis/1024`, while animated runtime point display uses the same scale but clamps only its CSS diameter to a maximum of `24px` (and applies renderer DPR after that). Contrast-ring widths remain unchanged. The visual cap never changes the full-size reconstruction/IoU raster, static PNG, descriptor, or artifact hashes.

`LoginParticleLogo.vue` sets a validated `--login-logo-aura` from the descriptor and uses it for the existing right-field radial wash while a managed effect is active; this changes atmosphere, not controls or text contrast. Without an active managed effect, the current login background remains, but no large particle/static logo is rendered.

Animate only when displayed long axis is at least 256 px and short axis at least 48 px. Otherwise show the personalized static rendition. Use displayed median stroke thickness `T` from twice the median distance-transform radius on the mask skeleton. Motion is a coherent, bounded 3D gaseous shader field with idle depth-phased drift bounded to `3.5..10px`; apply a `0.82..1.18` point-size depth cue while preserving source colors and alpha. Primary pointer interaction uses a fixed six-slot recent-impulse ring: only segments longer than `2 CSS px` qualify, each accepted event contributes at most `20 CSS px` of segment travel (there is no `20 events per frame` cap), influence is circular with a radius bounded to `18..32 CSS px`, aggregate impulse travel is capped at `14 CSS px`, and force scales with actual segment travel. Impulses have a `1.4s` lifetime. Neighbor influence is bounded at `0.32` and bounce at `0.22`.

Clicks and primary touch use a separate six-slot explosion ring. Each explosion has a `0.35s` fade/hold phase, refills over `2.4s`, and expires at `2.8s`; when all six slots are active, a newly arriving explosion is dropped and does not reset, replace, or extend any accepted event or its absolute recovery deadline. Overlapping explosions are deterministic and commutative, with no CPU per-particle loop or hot-path allocations.

Visual proof captures a reset scene at fixed simulation times and isolates impulse and explosion frames from the independent idle-drift baseline; wall-clock drift or a retry-selected frame cannot stand in for an interaction observation. The v5 density and motion contract remains normative: generated count `2,000..8,000`, eight reservations per meaningful component, `3.5..10px` idle drift, six cursor slots, six explosion slots, and the bounded lifecycle/recovery invariants above.

Desktop eligibility requires viewport width `>=960px`, height `>=651px`, hover/fine pointer, and enough measured free space. Reduced motion at startup is not an omission on eligible desktop: render the personalized static effect with its theme-selected neutral particle outline and assert a zero-ever trace for TresJS/Three import, particle fetch, WebGL, canvas, RAF, loop, timer, and pointer listener; the shared ordinary `logo-png` remains byte-for-byte unchanged. In a separate animation run that starts with motion enabled, a `false→true` preference change immediately replaces animation with that static artifact and synchronously stops/removes/disposes the canvas, RAF, loop, timer, and pointer listener; assert zero post-toggle callbacks/fetches, no re-import, and usable authentication. Mobile, coarse pointer, short viewport, and insufficient space omit only the large field. If no managed active revision is ready, render no effect field.

## 6. Descriptor, binary, and public delivery

HTML, auth favicon/render, navigation, mail, and site-config resolution use one central PostgreSQL-backed resolver that overlays active branding rather than trusting process cache or NOTIFY. A ready login snapshot includes required integer `pipelineVersion` and exactly three immutable derived URLs: the one shared `logo-png`, `particle-v1`, and `effect-static-png`, plus dimensions, aspect, particle count, median stroke, and aura color only when present. The `logo-png` URL and bytes are identical on login, navigation, favicon, and mail; legacy snapshots contain only the unchanged ordinary logo.

Expose the descriptor as `siteConfig.logoEffect`: `null` unless an active managed revision is ready and its `pipelineVersion` is an integer in the currently supported range `1..5`; otherwise it contains required `pipelineVersion`, immutable `logoUrl`, `particleUrl`, and `staticUrl`, `width`, `height`, `aspect`, `count`, `medianStroke`, and optional `auraColor`. `siteConfig.logoUrl` remains the ordinary-logo compatibility field and points to the same revision's shared `logo-png` URL after atomic activation. The active resolver reads and validates the exact pipeline version plus `normalizedWidth`, `normalizedHeight`, `particleCount`, `medianStroke`, and nullable validated `auraColor` directly from the active revision row, derives descriptor `aspect === width / height`, and cross-checks descriptor `width`, `height`, and `count` against the parsed `particle-v1` header before constructing the snapshot. The current client requires the descriptor field and version-gates sizing: v1 through v4 render with full core factor `1`, while v5 renders with exact core factor `2/3`, matching each pipeline version's static artifact. Invalid or unknown future versions fall back to ordinary legacy branding rather than attempting the particle effect.

The particle binary is v1 little-endian and exactly 56 bytes of header followed by one payload of exactly `12 * N` bytes; therefore `fileLength = 56 + 12*N` and no trailing bytes are valid. The complete header layout is:

| Offset | Type | Field and encoding |
|---|---|---|
| `0..3` | 4 bytes | Magic ASCII `TSEP` |
| `4` | `u8` | Version `1` |
| `5` | `u8` | Flags exactly `0x07`: sRGB (`0x01`), Y-up (`0x02`), and straight alpha (`0x04`) are all required; every other value is invalid |
| `6..7` | `u16` | Header length, exactly `56` |
| `8..11` | `u32` | Width in normalized source pixels, `2..4096` |
| `12..15` | `u32` | Height in normalized source pixels, `2..4096` |
| `16..19` | `u32` | Particle count `N`, `2,000..8,000` for generated pipeline-v5 artifacts; parser accepts `1..16,000` as its performance cap |
| `20..23` | `u32` | Payload length, exactly `12*N` bytes |
| `24..27` | `u32` | CRC-32/ISO-HDLC of payload bytes only |
| `28..31` | `u32` | XY block offset, exactly `56` |
| `32..35` | `u32` | Depth block offset, exactly `56 + 4*N` |
| `36..39` | `u32` | RGBA block offset, exactly `56 + 5*N` |
| `40..43` | `u32` | Size block offset, exactly `56 + 9*N` |
| `44..47` | `u32` | Seed block offset, exactly `56 + 10*N` |
| `48..51` | `u32` | File length, exactly `56 + 12*N` |
| `52..55` | `u32` | Reserved, exactly `0` |

Payload blocks are contiguous and typed as XY `Int16` (`4*N` bytes), depth `Int8` (`N`), source RGBA `Uint8` (`4*N`), size `Uint8` (`N`), and seed `Uint16` (`2*N`), all little-endian where multi-byte. Records are in ascending original source-pixel order and retain source RGBA with straight alpha; producers use pipeline-v5 deterministic eight-reserved-samples-per-meaningful-component generation in `2,000..8,000`, while the parser accepts `1..16,000` only as its hard performance ceiling. Validate sentinels, dimensions, exact block offsets and lengths, 64-bit-safe arithmetic, CRC-32/ISO-HDLC, file length, and no trailing bytes before allocating geometry.
Mount anonymous `GET` and `HEAD /_site-logo/:sha256/:role.:ext` before the common page/asset catch-all. Allow only `logo.png`, `particle.bin`, and `effect.png` roles/extensions; require canonical lowercase 64-hex SHA-256 and never expose `source`. Resolve and authorize by the composite `(role/kind, sha256)` key, verify the stored bytes' SHA-256 and the requested role before serving PostgreSQL bytes (optionally read-through cached by the same composite key), with exact `Content-Type` and `Content-Length`, strong digest ETag and conditional `304`, `X-Content-Type-Options: nosniff`, and `Cache-Control: public, max-age=2592000, immutable`; never vary on Cookie. Unknown, malformed, source, cross-role, traversal, or digest/content mismatches return `404`.

Hash URLs are immutable: replacement changes every active URL and needs no invalidation; old URLs remain identical during retention. Never overwrite same-path artifacts, use query-only cache busting, or key by mutable `assets.hash`. The route is independent of Guests `read:assets`, ACL/page protection, and sessions. No external fetch is permitted in processing or delivery.

## 7. Loading, fallback, accessibility, and cleanup

`LoginParticleLogo.vue` is synchronously imported by `client/components/login.vue` and has no static TresJS/Three import. It renders the static host and lazily imports `LogoParticleScene.vue`; authentication never waits. States are `omitted`, `static`, `loading`, `ready`:

- `omitted`: hard gate false; no field, import, request, renderer, loop, timer, or pointer listener; authentication is fully usable.
- `static`: active personalized static rendition is visibly present when available; otherwise the ordinary `.login-brand` is visibly present.
- `loading`: the active shared ordinary logo and personalized static rendition remain visibly present while import, WebGL2 check, descriptor/binary fetch, parse, compile, and first frame run.
- `ready`: first successful nonzero-size particle frame commits; the static rendition is retained below canvas until that frame, then canvas may fade in. Every named pre-ready failure and every ready/context failure synchronously leaves or restores the visible personalized static image; if that image is missing or corrupt, the shared ordinary logo remains visible and authentication remains usable.

A 1,500 ms wall-clock epoch deadline covers lazy import through first frame; no Promise timeout is described as native cancellation. Fail on import rejection, Vue descendant setup/render exception, unsupported WebGL2, invalid URL/origin/CORS/non-2xx/oversize/unreadable response, parser failure, zero size, renderer/TresCanvas error, shader error, loop exception, timeout, or context loss. Each callback/promise carries an epoch token; late completion cannot change state or authentication. Hard-gate loss tears down and omits; activity loss after ready retains one inert canvas and zero loop callbacks, then resumes the same epoch only when visible.

TresJS owns the canvas; the scene uses `TresCanvas` with transparent background, `clearAlpha=0`, antialias off, DPR `[1,1.5]`, and loop active only for animation. Use `WebGL.isWebGL2Available()`, `useLoop().onBeforeRender`, `shallowRef` for Three objects, one immutable `BufferGeometry`/`ShaderMaterial`/`Points`, and explicit disposal. Set `renderer.debug.checkShaderErrors = true` and route `onShaderError`; listen for native `webglcontextlost`.

Decorative host/image/canvas use `aria-hidden="true"`, `alt=""`, no role/focus/live region/tooltip, no keyboard handling, and `pointer-events:none` on canvas. Pointer input is passive primary mouse/pen on the bounded wrapper only; ignore touch/coarse/non-primary input, do not capture or prevent default, and do not log or transmit coordinates/timing.

Host lifetime retains media, visibility, free-space `ResizeObserver`, and `IntersectionObserver` monitors until host unmount. Scene-epoch teardown clears timers/listeners/hooks, stops and unsubscribes loop, aborts fetch, detaches callbacks, unmounts TresCanvas, disposes geometry/material/renderer exactly once, and releases refs. Hard-gate loss unmounts; hidden/offscreen ready state retains one canvas but no callbacks.
Reduced-motion startup is evaluated before any lazy import and therefore has a zero-ever resource trace. The runtime `false→true` preference toggle begins after animation has imported and acquired its resources; it shows the personalized static image immediately, then synchronously performs the scene-epoch stop/removal/disposal, with no post-toggle callbacks or fetches and no re-import, while authentication remains usable.
