## Security-relevant source observations

### Agent accounting, migration, provider failure, and toolchain boundary

Provider usage is accepted only as nonnegative safe integer directional and
total counts, with overflow-safe addition and `totalTokens` at least the
directional sum. Streaming usage must be cumulative and non-regressing.
Reservations account for the admitted total exposure; reconciliation records
provider totals, and unsettled exposure is retained against durable-goal
budgets rather than allowing a failed continuation to reacquire its full
allowance. Utility-provider accounting uses the same checked total-token and
cost boundaries. Provider failure classification exposes bounded stable codes,
stages, and status values instead of raw provider error material.

Migration `tsepistle-000031-agent-total-token-accounting.ts` validates all
legacy directional counters and their sum before adding and backfilling
`agentRuns.totalTokens`. PostgreSQL receives a nonnegative safe-integer check
and a directional lower bound. Invalid legacy state aborts the transaction;
the down path drops only the additive column. Diagnostic export strictly
decodes stored scalar forms, validates row invariants, and checks aggregate
addition for overflow.

The Bun cutover is consistently pinned to 1.4.2 in the package manager,
engine range, workflows, installer check, and digest-pinned build/runtime
images. Server startup checks the authoritative package engine range before
loading configuration or the application kernel. Workflow jobs that execute
Bun assert the expected toolchain version, and frozen dependency and generated
license inventory changes remain represented by `bun.lock` and
`third-party-licenses.json`.

### Notification authorization, disclosure, bounds, and client identity

Notification REST endpoints establish the authenticated human principal before
strictly comparing the canonical `X-Notification-Owner` value. Server response
envelopes carry the authenticated `ownerId`; client validators reject malformed
or foreign-owner success envelopes. Owner mismatch or HTTP 401 invalidates both
notification sources, aborts outstanding list/read work, clears cached private
items, advances the generation fence, and enters retryable authentication
recovery. Late requests cannot repopulate data after an account transition.

Watch listing remains owner-scoped and rechecks current page identity, complete
tags, and page-read authority before disclosing title, path, locale, visibility,
or actor metadata. Revoked or malformed rows and watcher state are purged only
within the authenticated owner's inspected IDs. The request has an absolute
500-candidate budget shared across unread and read phases. It advances from the
last raw processed boundary, preserves unread-completeness truth, and issues a
continuation when an unprocessed suffix remains.

Watch and approval continuation tokens are opaque UUIDv4 values, owner-bound,
TTL-limited, reused for equivalent boundaries, and limited to four live tokens
per owner. At global capacity, issuance fails rather than evicting another
owner's cursor. Approval listing similarly caps candidate work at 500, limits
visible results, prefilters ordinary participants, batch-loads minimal current
page projections, and rechecks page access and reviewer/participant eligibility
before disclosure.

Aggregate watch and approval GETs, individual watch state, and approval detail
responses use `Cache-Control: private, no-store` and `Vary: Cookie`. Internal
page links encode locale and each path segment. Ordinary watch-item activation
acknowledges the read mutation before same-window navigation and rechecks the
captured owner; modified clicks retain normal browser behavior.

### Approval, page-lock, and stale-write integrity

Approval detail, submission, and every transition receive the server session
ID. Password protection is checked against a current grant bound to page,
session, user, password version, and expiry. Submission and every transition
lock the current page row and evaluate transaction-scoped page authority and
page-lock state before mutation. A locked page returns `PAGE_LOCKED`; ordinary
page managers do not bypass the password boundary.

Submission requires the reader-captured canonical `sourceRevision` and rejects
stale content before creating a request. Resubmission is limited to the
submitter or administrator, additionally requires current page-write authority,
and compares the reader-captured revision while the page is locked. Review and
publication retain reviewer/assignee checks, stale-revision fencing, and
transactional transition/outbox writes. Stale failures preserve the reader's
comment and do not silently submit a newer revision.
