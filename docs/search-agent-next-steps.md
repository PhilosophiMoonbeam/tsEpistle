# Search and Agent: implemented foundation and remaining evidence

## Current contract

Search is a fast authorized page finder; the Wiki Agent is a separate workspace with explicit query, scope, and selected-source handoff. `operations.search` now owns one PostgreSQL lexical-plus-knowledge fusion for browser, REST/GraphQL, Agent, and MCP, and the Agent-local knowledge union is removed. Results carry canonical IDs and source revisions; hydration rejects an ID/revision/route mismatch rather than relabeling stale data.

Knowledge projection schema 2 / `wiki-knowledge-v2` is the only supported projection shape. It persists configured-dictionary `searchTokens` and bounded revision-matched `searchTerms`; schema-1 reads are unavailable and repair only reuses validated immutable intent. A `knowledge` result label means **knowledge hints**, never a verified claim, authority, tag, permission, or citation. Projection metadata selects a page; only an exact current or explicitly requested revision read supports a citation. Personal memory remains a separate owner-scoped snapshot and is not Wiki retrieval.

Structured syntax (quotes, standalone `OR`, token-boundary negation) cannot reach substring, fuzzy, acronym, or generated-hint fallback. Empty input is empty. ACL, publication window, protection, selected IDs, locale, and literal path scope filter candidates before caps; the raw 500-candidate cutoff no longer suppresses an authorized result. Public empty dates remain open where permitted, offset timestamps compare as instants, and invalid windows are not admitted. Protected body-derived material is excluded from direct lexical/knowledge matching; graph traversal enforces protected-boundary and current-revision succeeded receipt fences as verified below. Private search is requester-local, uses the same owner/system-manager authority for direct path reads, and caps private contribution at 50 independently of the public window.

## Utility boundary

The configured conformed utility profile is an operator-approved shared-content processor, not a requester-scoped read: preflight checks current revision/hash, public visibility, publication window, and password/protection state, but not requester/page-rule/anonymous-read ACL. It may therefore receive published shared ACL-restricted pages; retrieval still applies requester ACL. A private, protected, unpublished, scheduled, expired, or invalid-window source found at preflight makes no provider request. Revision/hash/eligibility are rechecked before output acceptance; a post-dispatch change discards output and finalizes safely without retracting already transmitted bytes. Requests have no tools, use strict bounded schema output, fill only declared gaps, and cannot write source, tags, authority, or verification; that does not make prompt content injection-proof or semantically true. `maxActive` uses the configured `globalConcurrency` value to cap knowledge leases across workers; it is separate from Agent-run slot accounting, not one combined chat/background provider pool. New `searchTerms` backfill may invoke utility once per eligible current page. There is no shared per-user background-cost accounting, per-user quota, or total backfill-cost quota, so operators must review shared-corpus/provider budget before deployment.

### Reviewer workflow for future release qualification

When ready to qualify search and agent enhancements for an official release, contributors must follow the non-circular exact-revision procedure:

1. **Freeze and commit source code:** Commit all search, agent, and core codebase modifications within the canonical security boundary (the entire `dev/` prefix, `server/`, `client/`, `shared/`, `deploy/`, `patches/`, `.github/workflows/`, `.github/actions/`, root release/config manifests, `tsconfig*.json`, and root packaging, repository attribute, and legal compliance files `.dockerignore`, `.gitattributes`, `LICENSE`, `NOTICE`; these files are essential to the boundary because .dockerignore governs container build context bounds, .gitattributes controls git archive export filtering and line endings, and LICENSE/NOTICE define distribution licensing terms).
2. **Calculate canonical digests:** Run `bun server/scripts/check-threat-model.ts --digest <revision>` to compute the canonical `coveredTreeDigest` and the SHA-256 `threatModelDigest`.
3. **Create immutable source-review record:** Author `docs/security/review-attestations/<id>.json` with `kind: "source-review"`, `schemaVersion: 1`, `repository: "PhilosophiMoonbeam/tsEpistle"`, `policyVersion: 1`, `reviewer: { identity, independent: true, reviewedAt }` (where `reviewedAt` is an exact UTC calendar date formatted as `YYYY-MM-DD`), `releaseEligible: true`, `source: { revision, baseRevision, coveredTreeDigest }`, and structural findings with `"resolved"` or `"accepted"` dispositions. Note that setting `independent: true` or `releaseEligible: true` in any `source-review` record (active or historical) strictly requires external cryptographic verification of a valid detached Ed25519 signature against `THREAT_REVIEW_TRUSTED_KEYS_JSON`; in-repository booleans alone never authorize release.
4. **Sign detached attestation:** Sign the canonical payload (`tsepistle-threat-review-attestation-v1\0` concatenated with compact JSON with recursively sorted keys, omitting `signature`) using the independent reviewer's Ed25519 private key, attaching the resulting signature object (`signature: { algorithm: "ed25519", keyId, value }`).
5. **Select active review in manifest:** Point `activeReviewId` in `docs/security/review-attestations.json` to the new record and register it in `records`.
6. **Commit attestation documentation:** Commit the review record and manifest updates under `docs/security/`. Because documentation (`docs/`) is excluded from the canonical security boundary, this commit leaves `coveredTreeDigest` unchanged, preventing circular revision invalidation.
7. **Execute gate validation with external trust root:** Verify with ordinary gate (`bun run threat-model:check`) and release gate (`bun server/scripts/check-threat-model.ts --release`). In CI, the threat checker receives `THREAT_REVIEW_TRUSTED_KEYS_JSON` from the public repository variable `vars.THREAT_REVIEW_TRUSTED_KEYS_JSON` (containing public verification keys rather than secrets, ensuring PR-safe availability across PR static checks, quality, and release gates). The release gate strictly requires a clean working tree with zero drift (with the sole canonical exception of the non-symlink regular file `server/.build-metadata.json` containing exact `revision` and `date` strings matching current HEAD and a valid canonical ISO timestamp in exact JavaScript `Date.toISOString()` canonical form `YYYY-MM-DDTHH:mm:ss.sssZ`; any malformed JSON, symlink, or revision mismatch fails closed), an exact covered-tree digest match against HEAD, zero blocking findings, and an authentic Ed25519 signature verified against a trusted key whose identity matches `reviewer.identity` for all independent or release-eligible source reviews. Missing trusted keys or signature invalidity blocks release; repository booleans alone never authorize release.
