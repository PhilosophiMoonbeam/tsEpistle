## 1. Git two-way storage is paused by deployment-wide offline mode

**Status: confirmed cause.** The saved Git target is enabled and set to two-way `sync` every 30 minutes, but the mounted `deploy/compose/config.yml` has `offline: true`. The running container reads the same value. On initialization, the storage runtime records every non-disk target as `paused` and skips creating its scheduled sync job. Page and asset events, manual remote actions, and scheduled sync are also blocked while this flag is true. Thus **Include this target** controls the saved target, while **Paused offline** describes a separate server-wide runtime restriction; there is no per-target unpause switch.

Evidence: `server/models/storage.ts:499-545`, `server/models/storage.ts:590-630`, `server/models/storage.ts:700-765`, `server/operations/storage-actions.ts:156`, `client/components/admin/admin-storage.vue:953-976`, and `client/components/admin/admin-storage.vue:1031-1038`. The live `storage` row reads `git|enabled|sync|PT30M` with status `paused`, message `Remote storage is paused in offline mode.`, and last attempt `2026-09-24T21:10:00.715Z`. The migration guide explicitly says to keep `offline: true` during migration validation (`deploy/migrations/from-wikijs-v2/README.md:14`); that setting remains in the deployed config.

The container's Git worktree is clean at `b5a3457` (2026-09-17), and a read-only `ls-remote` from *inside the container* returned the same commit for remote `master`. Git credentials and basic remote reachability therefore worked for this read. The database's latest page update is `2026-09-24T17:16:00.437Z`, with 28 page rows updated after that Git commit. This shows newer database content that the paused target has not exported; it does not establish that every one of those rows needs a new Git commit. A host-side Git probe failed because the configured SSH key path exists only inside the container, so that probe is not evidence of a deployed credential failure.

**Follow-up for an authorized repair:** review the intended meaning of server `offline`, then change the deployment setting through the normal configuration/deployment path if outbound Git access is intended. Before allowing the first two-way run, compare the database pages and remote branch and preserve a recovery copy of the database and `/wiki/data/repo`: `sync()` fetches, rebases or reattaches history, pushes, and imports changed files (`server/modules/storage/git/storage.ts:528-604`). Verify the target becomes active, an actual sync attempt completes, a known local edit appears remotely, and a controlled remote edit imports. Do not treat toggling **Include this target** as an unpause operation.

## 2. “Apply app update” does not start automatically

**Status: code path confirmed; user-visible frequency not measured.** A newly installed waiting service worker sets `updateReady` and shows **Apply app update**. The only production call to `requestPwaUpdate()` is the button handler. That call invokes `registration.update()` if needed and sends `PWA_PREPARE_UPDATE` to the waiting worker. The worker's safe-client vote and `skipWaiting()` path starts only after that preparation message. `onUpdateReady` is an optional callback, but the application does not register one that starts preparation. This explains why the button can remain waiting indefinitely while a tab stays open; it is not currently an automatic update action.

Evidence: `client/helpers/pwa.ts:707-781`, `client/helpers/pwa.ts:1196-1269`, `client/components/pwa/pwa-status.vue:60-80`, `client/components/pwa/pwa-status.vue:209-217`, `client/service-worker.ts:530-610`, and `client/service-worker.ts:745-760`. Even after a manual request, preparation can defer if another open page does not answer the safety vote within 20 seconds (`client/helpers/pwa.ts:396-405`), or if a page has unsafe current work. The UI gives a generic note but does not make the idle-versus-deferred distinction obvious.

**Follow-up for an authorized repair:** decide whether automatic activation is intended, and if so start the existing safety protocol when an update becomes ready; keep the current draft/reload safety gate. Test with one safe tab, multiple tabs, and an unsaved editor, recording whether the waiting worker activates and the page reloads only when safe. If activation is meant to require a click, make that policy explicit in the UI.

## 3. “Offline sync” covers different behaviors and needs a browser reproduction

**Status: terminology and code path confirmed; reported never-sync symptom not reproduced.** Browser offline page sync is a pull of selected server page snapshots into local IndexedDB, triggered on startup and on online, foreground, and identity changes (`client/client-app.ts:89-176`, `client/helpers/offline-sync.ts:444-545`). It is separate from the server's `offline: true` setting and from Git storage. Editor drafts saved locally while disconnected deliberately become **needs review** on reconnection and are not submitted automatically (`client/helpers/offline-editor-drafts.ts:1497-1535`, `client/components/editor.vue:120-175`). Consequently, a user expecting offline edits to upload without review may perceive that as failed sync even when page downloads work as designed.

**Follow-up for an authorized investigation:** in an authenticated browser on the deployed origin, save one page for offline use; inspect the offline page's last attempt, pending count, and error; disconnect, read it, reconnect, and verify the snapshot refreshes. Separately edit offline, reconnect, and inspect the draft review/publish flow. Record the browser, tab state, page ID, timestamps, IndexedDB diagnostic, and any failed snapshot request. If downloads still fail, trace the connection probe and coordinator result before changing code. Do not infer a browser sync defect from the Git pause: they have different controls and data paths.
